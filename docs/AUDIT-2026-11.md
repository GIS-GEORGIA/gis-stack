## Phase 2 (deployment reliability) - findings and result

Existing before: journal of operations, remote/local lock, preflight, `gisstack-backup` pre-restore backups for restores. **Missing:** a record of what a deployment changed, any post-deployment health check, any way back after a bad deployment (`existing.run` has its own backup flow, unchanged).

Implemented (`gisstack/deployments.py`, hook in `deploy.deploy`, `services.rollback_*`, `/deployments/history|rollback/plan|rollback`): records, health verification, rollback = re-apply an earlier healthy configuration, with refusals, current-secret preservation, idempotency, audit events. See `docs/DEPLOYMENTS.md`.

Not possible (reported to the user instead): undoing package installs, database migrations, removing programs the newer configuration added, automatic rollback without a stored healthy record. Automatic rollback on failure is deliberately **not** done: a rollback is always an explicit, confirmed, audited action.

## Phase 3 (security and compatibility) - findings

* **Legacy `/api/*`:** 28 routes; 27 have a `/api/v1` successor and already answer with `Deprecation: true` and `Link: rel="successor-version"`. `/api/logout` has none. They cannot be removed yet: the classic page `/` calls 18 of them. Safe path: retire the classic page first (every workflow is in the dashboard except deploy/clean/projects/existing-programs wizards), then remove the aliases in one release with a CHANGELOG migration note.
* **Classic page CSP (`unsafe-inline`):** *not removed.* It has 2 inline `<script>` blocks (one ~640 lines), 1 `<style>` block, 13 `style=` attributes, 1 `onsubmit=`, and more `style=` inside HTML strings built in JavaScript (e.g. the services table and update box). Removing `unsafe-inline` means moving all of that to static files and replacing every inline style, then re-testing every workflow of that page in a browser - not safe to do as a side change. The new dashboard pages all run under the strict CSP, which was not weakened.
* **Reviewed, no change needed:** token/session handling, CSRF header on every state-changing route, rate limiting, Host allow-list, request size limit (existing tests in `test_web_security.py`, `test_api.py`); scope matrix test covers every route, including the new ones.
* **Fixed in this work:** rule-editor errors no longer contain server file paths; deployment records and audit events contain no secrets (tested); rule/deployment files are written 0600 atomically.
